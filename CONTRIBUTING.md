# Contributing

Thanks for taking the time. These are the organization-wide defaults; individual
repositories may add their own rules on top.

## Before you start

- For anything non-trivial, open an issue first so we can agree on the approach.
- Check open issues and pull requests — someone may already be on it.

## Pull requests

1. Branch off `main` — `feat/short-description`, `fix/short-description`, `chore/…`.
2. Keep the change focused. One concern per pull request.
3. Write commit messages in [Conventional Commits](https://www.conventionalcommits.org/) style:
   `feat: add wallet connect`, `fix: handle empty response`, `docs: …`, `chore: …`.
4. Make sure lint and tests pass locally before pushing.
5. Fill in the pull request template — what changed, why, how it was tested.
6. Do not force-push after a review has started; add commits instead.

## Code style

Follow whatever the repository already uses — formatter and linter configs are
committed for a reason. If there is no config, match the surrounding code.

## Reporting bugs

Use the bug report template. A reproduction beats a description.

## Security

Do **not** open a public issue for security problems. See [SECURITY.md](SECURITY.md).
